# BeeOps — Admin Front-End

Internal operations web app for **Bee Transportation Corporation**
(CTCP Vận Chuyển Con Ong, tax code 0318823069). This repository holds the admin front-end;
the API lives in a separate repository (`bee-transportation-be`).

BeeOps replaces the per-person spreadsheets that used to hold orders, quotes and progress.
A sale creates a standardised order, the system distributes it to every department responsible
for that service, the departments quote it competitively without seeing each other's numbers,
the sale compares and closes, and execution is tracked through the milestone set generated at
close time.

---

## Quick start

Requires Node 22 and a reachable BeeOps API.

```bash
npm install
cp .env.example .env      # adjust VITE_API_PROXY_TARGET if needed
npm run dev               # http://localhost:5173
```

| Script | Does |
|---|---|
| `npm run dev` | Vite dev server with `/api` proxied to the backend |
| `npm run build` | `tsc -b` then a production bundle into `dist/` |
| `npm run preview` | Serve the built bundle |
| `npm run lint` | ESLint, `--max-warnings 0` |
| `npm run format` | Prettier over `src/` |

### Environment

| Variable | Meaning |
|---|---|
| `VITE_API_BASE_URL` | Base URL of the API. **Leave empty in development** so requests go through the dev proxy and stay on one origin — the session cookie is `SameSite=Lax` and is dropped across origins. |
| `VITE_API_PROXY_TARGET` | Where the dev server forwards `/api`. Defaults to the deployed API `http://167.254.68.111`; set it to `http://localhost:8087` to work against a local backend. |
| `VITE_USE_MOCK` | Serve screens from `src/mocks` instead of the API. Off — the mock layer covers authentication only and exists for offline work. |

## Domain model in brief

**Ten services**, each owning an order-code prefix: `CON` consulting · `CUS` customs ·
`DOM` domestic · `PRJ` project/oversized · `LIF` lifting · `MMT` multimodal · `PKG` packing ·
`CBT` cross-border · `BRK` shipbroking · `RNT` equipment rental.

**Order code** `[SERVICE]-[YYYYMMDD]-[NNN]`, the sequence resetting daily per service. It is
generated by the backend and never composed on the front-end.

**Lifecycle**
`new → distributed → quoting → awaiting_selection → awaiting_customer → closed → in_progress →
completed`, with `rejected` and `cancelled` as separate terminal states.
`awaiting_customer` can return to `quoting` when the customer asks for a revision.

**Five roles** — `users.roles` is an array, so a person may hold several and their permissions
are the union.

| Role | Does | Sees which orders | Sees which revenue |
|---|---|---|---|
| `admin` | Organisation, catalogue, routing matrix | All | Company |
| `leader` | Read-only oversight | Their department's orders | Company |
| `manager` | Assigns work in own department, quotes | Their department's orders | Own department |
| `sale` | Creates orders, compares quotes, closes | Orders they created + their department's | Own orders |
| `staff` | Claims orders, quotes, updates milestones | Own assignments + department queue | Per-order value |

Plus a per-user flag `canViewCompanyReport` granting the company dashboard without a role change.

**Reading orders and reading reports are separate permissions.** Only `admin` reads orders
across every department; `leader` and anyone holding `canViewCompanyReport` keep the
company-wide dashboard and revenue report but see order rows only within their own department.
The consequence is deliberate and visible: those users read company totals they cannot drill
into. The backend settles it in `common/scope/can-read-all-orders.ts` (orders, amounts, sealed
quotes, discussion) versus `is-company-wide.ts` (reports only).

**Three axes are never mixed**: the role decides *what you may do*, the scope decides *whose
rows you see*, and money visibility decides *whether the amount is populated at all*. The
backend is the authority on all three; the front-end mirrors them only to avoid rendering
controls that would fail.

**Sealed quotes**: when several departments quote the same order, each sees only its own quote.
Only the owning sale and `admin` see them side by side.

## Architecture

```
component  →  hook  →  service  →  adapter  →  apiClient  →  backend
```

- Components import view types only; they never see an `Api*` shape.
- A backend field rename touches one adapter, never a component.
- Endpoint strings live only in `src/services/apiEndpoints.ts`.
- `null` is preserved and never coerced. `finalAmount: null` means "you may not see this
  amount", not zero, and renders as an em dash.

```
src/
├── components/      shared primitives — PageContainer, SectionCard, DataTableShell,
│   └── form/        StatusChip, ConfirmDialog, EmptyState, and the validated form fields
├── constants/       roles, permissions, order status and its colour tones, pagination
├── hooks/           useAsyncResource, usePermissions, useOrderFilters, useProvinces, …
├── layouts/         DashboardLayout, AuthLayout, sidebar and header
├── locales/         vi.json (default) and en.json — the only place Vietnamese text lives
├── pages/           admin · customers · dashboard · notifications · orders
├── routes/          routePaths.ts, AppRoutes.tsx, ProtectedRoute.tsx
├── services/        apiClient, apiEndpoints and one service file per resource
├── store/           session and notification providers with their contexts
├── theme/           palette, typography, component overrides
├── types/           view types
└── utils/           formatters, validation, storage
```

Two conventions carry most of the consistency:

**The list pattern is written once.** `DataTableShell` owns it — `CircularProgress` on first
load, `LinearProgress` on refetch, a dismissible error `Alert`, an `EmptyState` when there are
no rows, pagination at the bottom. Search is debounced 350 ms, any filter change resets to page
one, and filter state is mirrored into the URL so a filtered view can be shared.

**Mentions are filtered server-side.** Typing `@` in the discussion box queries
`GET /orders/:id/mentionables`, which returns only people who may read the thread being written
into — never a client-side filter over the user directory. Removing the inserted `@Name` from
the draft drops the mention with it, so nobody is notified about a message that does not name
them. A mention raises a `mention` notification delivered live over SSE.

**The department queue shows what happened to the order.** Cancelling an order does not touch
the per-department state, so a cancelled order still reaches the queue as `pending`. The row
reads the order status too, renders "Đã hủy" and disables claim, assign and pass rather than
offering an action the backend answers with `409`.

**The theme owns the look.** Card radius and shadow, table head and row hover, input shape,
and tabular figures so a column of money lines up — a screen that needs a different look
changes the theme, not itself. Input validation lives in the shared fields under
`components/form/`: `NumberField` cannot hold a non-number, `PhoneField` refuses letters,
`PasswordField` carries a reveal toggle, `DateField` is a locale-aware picker.

### Backend contract essentials

- Global prefix `/api`; Swagger at `/api/docs`, JSON at `/api/docs-json`.
- **Auth is a JWT in an httpOnly cookie.** Axios uses `withCredentials: true`. There is no
  bearer token and nothing auth-related in `localStorage`; `GET /auth/me` is the only source of
  roles.
- Success envelope `{ success, data, meta }`, unwrapped by the response interceptor.
- Error envelope `{ success, error: { code, message, statusCode, details? } }`. The message is
  Vietnamese and safe to show; screens branch on `status`, never on message text.
- Every list answers `{ items, total, page, limit }` and takes `?page=&limit=`.
- `404` is deliberately returned for rows outside the caller's scope, so an out-of-scope order
  renders "not found" rather than "no permission".
- `409` covers both an illegal state transition and a unique-constraint violation.
- Money is a JSON number of whole dong. Never do currency arithmetic in a component; format
  through `formatCurrencyVnd`.

## Known issue on the deployed host

`http://167.254.68.111` serves the current backend code over a database that never received
`db/migrations/001-qa-fixes.sql`. The Prisma `Order` model maps `reject_note` and
`cancel_reason`, two columns only that migration creates, so **every endpoint touching order
rows answers `500` there** while everything else answers `200`. The same build over a migrated
database works. Nothing on the front-end needs to change — the order screens surface the
backend's message in a dismissible alert — but F1 to F6 are unusable on that host until the
migration runs. Details, repro and the fix are in `.claude/qa.html` under **QA-26**.
