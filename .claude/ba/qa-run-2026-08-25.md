# QA fleet run — 25/08/2026, deployed backend

14 tester charters (haiku) in two waves against `http://167.254.68.111` through
the dev proxy, per `.claude/ba/BA.md`. Wave 1: auth, intake, service fields,
queue, quoting, closing, org admin. Wave 2: permissions, lifecycle, list,
detail/collaboration, milestones, dashboard, monkey. Every surprising finding
was re-verified by the parent before being accepted; a tester's word alone was
never enough.

Environment was seeded first (the deployed DB was empty): departments
`QA Phòng A` (DOM, CUS, RNT, PKG) and `QA Phòng B` (DOM, CBT, LIF), eight
role accounts, both departments covering DOM for the competition mechanics.

## Confirmed findings

| ID | Where | Severity | What |
|---|---|---|---|
| QA-31 | Backend | **High** | A **cancelled order accepts a quote**: `POST /orders/21/departments/1/quote` on a cancelled order answers `201` and records `quoteVersion: 1, amount: 1000000`. The state machine guards close/reject/select, but the quote endpoint never checks terminal states. The UI hides the quote form on cancelled orders, so exposure is API-only — but a department hitting the API can spend effort quoting a dead order, and terminal rows mutate. Reproduced by the parent end-to-end. |
| QA-32 | Backend | **Medium** | **Pass accepts an empty reason**: `POST .../pass` with `{"reason": ""}` and with `{"reason": "   "}` both answer `201`, although the specification (§6-F2) makes the reason mandatory. A missing key is refused (400), so the DTO lacks `@IsNotEmpty` + trim. The UI dialog blocks the empty case, so this too is API-only — but the sale can end up staring at a pass with no reason. |
| FE-01 | Front-end | Low | `/orders/abc` (non-numeric id) renders the **order list** page with a raw English backend message "Validation failed (numeric string is expected)" in the alert, instead of the not-found page that `/orders/-1` and `/orders/999999` correctly show. The order-id param should be validated as a positive integer before any fetch; garbage renders NotFound per I-5. |
| FE-02 | Front-end | UX | `/orders?page=-2` surfaces the backend's raw English `page must not be less than 1` in an error alert with an empty table. Nothing breaks, but a tampered/mistyped page number would serve users better clamped to page 1 silently. |

## What passed — the spec holds

All ten BA.md invariants survived everything thrown at them:

- **Sealed quotes (I-2)** — verified per persona at API and UI: each department
  sees only its own amount before, during and after selection; the owning sale
  and company roles see all; unchanged after losing.
- **Money visibility (I-1)** — losing manager gets `null` (renders —), winning
  side and company roles see the number, the other sale gets 404.
- **Revenue lock (I-3)** — closing locked 4,500,000; later quote edits refused;
  post-close edits demand `changeNote`; dashboard month bucket carries exactly
  the closed sum; the cancelled order stays out of the win-rate denominator;
  a fresh sale's win rate renders — (null), not 0%.
- **State machine** — 12 transitions walked including the revision loop; every
  illegal jump answers 409 with a Vietnamese message naming both states;
  concurrent same-department claim answers a clean conflict.
- **Milestones (I-9)** — generated at close, sequential enforcement (400
  `Phải xử lý mốc "Đã điều xe" trước`), skip requires a note, last milestone
  flips the order to Hoàn thành, template edits never touch closed orders,
  the losing department is refused with the right message.
- **Per-service input boxes** — schema-driven form per service, unknown
  `serviceData` key 400s naming the field, retire-not-delete for used fields,
  fieldKey immutable.
- **Order intake** — code format and per-service daily sequence correct;
  hand-typed duplicate customer names do not split history.
- **Permissions matrix** — staff cannot create orders (403), leader is
  read-only everywhere, `canViewCompanyReport` opens exactly the company view.
- **Lists** — every filter matched its API count, combined filters compose,
  URL round-trips, sort whitelist enforced, Excel export delivers.
- **Hostile input** — XSS/SQL/template-injection strings land as inert text,
  no console errors, no 500s; mobile 390×844 clean.

and service fields have a DELETE endpoint. So the QA data was **neutralised, not
row-deleted**:

- Every non-terminal order cancelled (all orders now terminal); orders cannot be
  deleted through the API.
- All ten QA accounts (`qa.*`, `QA25-*`) locked; only the two original admins
  (`admin@beetransportation.vn`, `phongbantesting@gmail.com`) stay active.
- All QA departments deactivated (none active).
- The uploaded test file deleted.
- The retired service field `qa25_retire_test` (CUS) stays inactive — an order
  carries a value for it, so the backend retires rather than deletes it; it will
  not appear on any form.
- Local temp files removed.

**Fully clearing the rows needs the backend team to truncate or a direct DB
reset** — the API cannot delete orders, customers, users or departments by
design. The host was near-empty before this run, so this is test scaffolding on
a test host, not production data.
